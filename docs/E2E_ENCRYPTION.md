# E2E-шифрование синка — дизайн-спайк (Фаза 22, решение не принято)

Статус: **предложение**. Код не написан; документ — основа для решения go/no-go.

## Зачем

Сейчас self-host сервер видит содержимое задач и заметок открытым текстом
(см. «Ограничения» в SERVER_SYNC.md). E2E-шифрование делает приватность
сквозной: даже администратор сервера читает только шифроблобы. Это финальный
аргумент приватного moat ProdNote.

## Модель угроз

Защищаемся от: чтения содержимого на сервере (компрометация сервера/БД/бэкапов,
любопытный хостер). **Не** защищаемся от: компрометации устройства,
слабой пассфразы, метаданных (количество сущностей, типы, время правок —
серверу видны по необходимости синка).

## Схема

- **Ключ.** Пассфраза пользователя → PBKDF2 (600k итераций, соль per-workspace)
  → AES-256-GCM workspace-ключ. Ключ живёт в памяти вкладки; соль хранится на
  сервере рядом с воркспейсом. Смена пассфразы = перешифровка всего (фоново).
- **Что шифруется.** Payload каждой сущности сериализуется в JSON и шифруется
  целиком (nonce per-запись). Метаданные, нужные серверу для LWW, остаются
  открытыми: `entity_id`, `client_updated_at`, `server_revision`, `deleted_at`,
  тип сущности.
- **Сервер: blob-per-entity.** Нормализованные таблицы (`tasks`, `notes`, …)
  вырождаются в `entities(workspace_id, type, entity_id, ciphertext, client_updated_at,
  server_revision, deleted_at)`. LWW-guard `client_updated_at < excluded...` и
  tombstone-механика синка v2 переживают переход без изменений — они и сейчас
  не смотрят в payload.

## Что ломается / чем платим

1. **Web Push теряет содержимое.** Серверный планировщик (Фаза 13) читает
   события/дедлайны — с E2E он не сможет. Варианты: (а) клиент при каждом пуше
   загружает на сервер зашифрованный *расписание-манифест* + отдельный ключ
   только для напоминаний (компромисс); (б) push с генериком «У вас событие в
   14:30» по открытому минимуму (время, без названия); (в) push отключается при
   включённом E2E. Рекомендация: (б) — честный компромисс.
2. **ICS-прокси** не затронут (фид внешний), но события из подписок шифруются
   как обычные.
3. **Отладка/миграции на сервере** становятся слепыми; фиксация багов синка —
   только на клиенте.
4. **Забытая пассфраза = данные только локально.** Обязателен экспорт-ремайндер
   и явное предупреждение.

## Трудоёмкость (оценка)

- Сервер: новая таблица + переходная миграция (двойная запись → переключение) — ~2 фазы.
- Клиент: crypto-слой (WebCrypto, ~200 строк) + шифрование в diffWorkspaceForPush /
  расшифровка в pull + UI пассфразы + перешифровка — ~2 фазы.
- Push-компромисс (вариант б) — ~1 фаза.
Итого ≈ 5 фаз обычного размера, самый большой инфраструктурный кусок после синка v2.

## Прототип для замера (когда будет go)

Шифрование одной коллекции (notes) за флагом `?e2e=1`: замерить оверхед
на воркспейсе в 5к сущностей (ожидание: единицы миллисекунд на запись,
десятки на полный pull — WebCrypto аппаратно ускорен).
